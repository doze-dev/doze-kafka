# Trace

Stage TRC. Size M. Follows [../01-protocol.md](../01-protocol.md); the common acceptance criteria there apply in full, and this page adds Trace's own. Foundation items (`A1`, `A4`, `B3` ...) are in [../00-foundation.md](../00-foundation.md).

## 1. Summary

Trace follows one trace id through every topic: the console asks the broker, by timestamp, which records were written around a message, reads them with an ordinary consumer, and lists the ones whose headers carry the id (W3C `traceparent`, B3 single and multi header, or the header named by `--trace-header`), with which consumer groups have committed past each. The broker indexes nothing about headers and should not. Everything is console code over three existing Kafka APIs (Metadata, ListOffsets, Fetch) plus OffsetFetch/ListGroups for the "groups past it" column.

It is small in code (about 1,200 lines in `console/` plus the timestamp lookup in `internal/storage/log/timestamps.go`) and large in claims: the page promises a "budget", a true "what was left unread" report, a 64-bit/128-bit match, and a statement of which groups have read past each record. Most findings below are places where one of those promises is not kept, or cannot be kept by the current scan loop.

Peers: [topics](topics.md) (the record drawer's "Follow this message" is the only entry today, and the Inspector from A1 replaces it), [groups](groups.md) (committed offsets, lag, the offset-set action that makes "read" ambiguous), [traffic](traffic.md) (the scan's consumer is a client the wire dock sees), [access](access.md) (the scan runs as the console principal, so ACLs decide what it can read), [cluster](cluster.md) (transactions: aborted records, control batches).

Packages owned: `console/trace.go`, `console/trace_scan.go`, `console/handlers_trace.go`, `console/templates/trace.html`, `backend.newReader` (`console/backend.go:669`), ListOffsets-by-timestamp (`internal/broker/listoffsets.go`) and the timestamp lookup in `internal/storage/log/timestamps.go`, the `--trace-header` flag (`cmd/doze-kafka/cli.go:370`) and config key (`internal/config/config.go:337`, `file.go:47`).

An important correction to the brief's vocabulary: **there is no time index on disk.** `timestamps.go:8` says so: each segment keeps, in memory, its largest timestamp and a sparse list of marks (one per 64 KiB), built the first time a lookup asks by reading every batch header. Board Tc-02 ("found through each partition's time index") and the comment at `trace_scan.go:193` ("the broker's time index") are loose wording for that. The correctness and cost analysis below is of the in-memory marks.

How the areas the brief singled out were looked at, and what they came to:

- **Time lookup at boundaries, segment rolls, compaction, retention.** Read `timestamps.go` end to end and the callers. The algorithm is sound as written: marks hold the largest timestamp before a batch, `startFor` picks the last mark whose predecessors are all below the target, the walk skips batches wholly below the log start and below the target, and records are decoded only inside the first qualifying batch. Segment roll: a lookup holds `p.mu`, so a roll cannot interleave. Compaction: `swapSegment` replaces the `*Segment` through `openSegment`, so the cache starts empty; no stale marks. Retention: `visibleFrom` plus the `logStartOffset` checks handle a head segment partly or wholly deleted. No wrong answer was found; what is wrong is the cost (TRC-17), silence on corruption (TRC-18) and missing boundary tests (TRC-16, TRC-18). `OffsetOfMaxTimestamp` recomputes the visible maximum only for the first segment, correct because later segments are wholly visible.
- **Scan budget and "what was left unread".** True when the budget is the thing that stopped the scan (record budget: `left` is built from the plan; time budget: from `reached`). Not true for the other ways it stops (TRC-1, 2, 26).
- **64 vs 128 bits.** Implemented as the boards say; whether it is the right rule is TRC-15.
- **traceparent/b3 parsing, fuzzed.** Run as a table in the scratchpad (TRC-5, 6, 7); a native fuzz target is owed (TRC-20). Safe against ReDoS (RE2).
- **Concurrency, memory, storage, expiry, Stop.** TRC-8 to 12.
- **"Which groups have committed past each record" computable?** Yes, for the part it says: `OffsetFetch` gives the committed offset (the next offset to consume), so `committed > record offset` is exactly "committed past". It is not computable as "read", and not for a group with no commit on the partition, nor for a group whose offsets expired or whose topic was recreated. The board's `lag 14` is computable as end offset minus committed (the `end` map already exists in `planTrace`); say which of the two lags it is. (TRC-13, 14.)

Prior art. Apache Kafka answers time lookups with a `.timeindex` file per segment (KIP-33; ListOffsets by time is KIP-79; the max-timestamp query is KIP-734), which is the persistent form of what `timestamps.go` rebuilds in memory; a persisted sidecar is the straightforward fix for TRC-17. Redpanda Console and Kafbat/AKHQ browse messages by offset and timestamp and filter by header, but none builds a cross-topic trail. Trace headers on Kafka records are written by OpenTelemetry's Kafka client instrumentation as W3C `traceparent` (and by Brave's Kafka tracing as B3 headers); the consoles that exist for tracing (Jaeger, Zipkin) get spans from the application, not from the broker, which is why this page is explicit that it can only see what apps propagate. KIP-714 (client metrics) is metrics, not traces, and the existing `observability.md` already says so. Read-only scans with a budget and an honest "partial" banner have no direct Kafka precedent; the closest is the Confluent Control Center message viewer's bounded search.
