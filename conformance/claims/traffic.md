# Claims: Traffic stage

The stage's recording queue (R1 to R9, `plan/stages/traffic.md` section 8) and the
claims the console's explainers make about Kafka. A `recorded` row's scenario was run
against `apache/kafka:4.3.1` in Docker, its answers are the committed file named in
Evidence, and doze-kafka was made to answer the same (the replay, `go test
./conformance`, runs without Docker). Two rows are not recorded and say so: R9b is
`doc` and R7b is `memory`.

The scenarios that need Kafka to apply an interval define a `CLIENT_METRICS` resource
with the five seconds doze-kafka always uses, as their first step, and then run in real
time against both brokers: they are replayed. doze-kafka refuses that first step (it
has no such resource), which is the one written-down difference in them. One scenario
is "not replayed", `telemetry-subscription-change`: it changes the resource under a
client, which cannot happen here.

A broker with nothing configured does not advertise `GetTelemetrySubscriptions` and
`PushTelemetry` at all (row R5), but answers them when sent. The recordings below are of
the raw requests, which is what a client that does speak them (a plugin implementing
`ClientTelemetry` is configured) gets.
