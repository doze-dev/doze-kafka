# Claims: who a connection is (SASL/PLAIN and SASL/SCRAM)

What `apache/kafka:4.3.1` answers to every login a client can send, right or wrong,
in order or out of it, and who its authorizer then takes the connection to be. Two
scenarios, both replayed against doze-kafka on every test run:

- `sasl-plain`: a listener offering PLAIN, three users in its JAAS configuration.
- `sasl-scram`: a listener offering PLAIN, SCRAM-SHA-256 and SCRAM-SHA-512; the SCRAM
  credentials are written through `AlterUserScramCredentials` before the script starts
  (4096 iterations, a salt made from the user's name; `conformance/targets.go`).

Both brokers run an authorizer that refuses what no ACL allows (`StandardAuthorizer`;
`acl-default = "deny"` here), and two topics, `for-alice` and `for-bob`, each of which
one user may describe. A Metadata request for both is the question "who am I": the
steps named `…-who` answer 0 for the topic the connection's principal may see and
TOPIC_AUTHORIZATION_FAILED (29) for the other. It is asked after every exchange, so a
connection that ended up as somebody other than the user whose password was proven
would show, and a connection Kafka closed shows as closed.

In a recording a SASL token is written as text. In a SCRAM message the server's half
of the nonce is `<server-nonce:N>`, the salt `<salt>`, the server signature
`<server-signature>` (the script checks it against the password and fails the run if it
is wrong), and a proof the script computed is `<proof of PASSWORD>`.

Not recorded: TLS (a client certificate as the principal), SASL over TLS,
`SaslHandshake` v0 (tokens without Kafka's framing; doze-kafka does not serve it),
OAUTHBEARER, GSSAPI, delegation tokens, re-authentication (KIP-368, off unless
`connections.max.reauth.ms` is set; with it off Kafka answers a second login
ILLEGAL_SASL_STATE, rows A7 and A18).
